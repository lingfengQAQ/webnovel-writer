# 知识库策展规则

> 版本：1.0（2026-07-16）
> 适用角色：v7 开发者、知识策展人员和产品维护者。作品作者不参与通用知识扩库流程。

## 1. 正式库与工作区

- `v7/references/` 只保存已通过开发审查的正式条目。
- 候选材料、来源、逐条裁决和拒绝理由保存在对应 `.trellis/tasks/` 任务中。
- 禁止在正式库旁建立长期 `_候选/`、`_草稿/`、作者投稿或自动扩库目录。
- 单本作品的设定、人物、名称和知识选择只进入作者书仓，不得自动晋升为通用知识。

## 2. 两级治理

### 2.1 普通策展

适用于既有边界内的新增、文案修正、拆分、合并、废弃和别名调整。普通策展不得改变维度定义、调用阶段或公共字段。

### 2.2 架构变更

以下任一情况必须升级为架构变更：

- 新增或删除顶层维度；
- 改变维度定义、相邻边界或调用阶段；
- 引入跨维公共字段或新的持久化层；
- 批量移动一组条目；
- 现有调用者无法消费拟新增知识。

架构变更必须更新 `维度宪章.md` 和 `调用者与字段矩阵.md`，列出目录、运行时、书仓、测试和全部受影响条目，并单独获得确认。

## 3. 新条目准入

候选必须同时通过五项检查：

1. **独有问题**：能指出现有条目没有覆盖的真实创作问题；
2. **独有动作**：提供不同于近邻条目的可执行方法；
3. **独有失败模式**：能说明何种错误只有该方法可以识别；
4. **明确触发**：调用者能根据输入判断何时需要它；
5. **可区分**：两名审查者能依据宪章把它与相邻条目分开。

只增加题材词、改名复述或提供成品剧情模板的候选直接驳回。条目数量不是验收目标。

## 4. 策展流程

1. 在 Trellis 任务中记录来源、发现的问题和候选正文。
2. 指定主要调用者、调用阶段和预期产出。
3. 依据维度宪章确定唯一归属；含多个独立方法时先拆分。
4. 与同维及相邻维度做近重复检查。
5. 按调用者需要重写为可迁移原理、操作方法、边界和失败模式，删除具体人名、书名、数值模板和成品情节。
6. 按字段矩阵删除无消费者字段；新增字段必须和消费者、测试同批提交。
7. 通过格式检查、行为测试和独立内容审查。
8. 记录保留、锐化、拆分、合并、移动、废弃或驳回裁决及理由。
9. 完成开发治理签收后才进入正式目录。

## 5. 近重复裁决

不得只比较名称。依次比较：

- 解决的问题是否相同；
- 建议动作是否相同；
- 失败模式是否相同；
- 调用阶段和产出是否相同。

处理方式按以下优先级选择：

| 情况 | 处理 |
|---|---|
| 问题、动作、失败模式实质相同 | 合并，保留信息更完整的 canonical 条目 |
| 同一问题但动作确有不同 | 分别保留并锐化选择条件 |
| 一个是另一个的必要子步骤 | 合并为正文小节；只有能独立调用时才保留子条目 |
| 材料包含多个独立问题 | 拆分后分别归位 |
| 只是题材化改写 | 保留通用原理，用适用条件表达；无消费者时不加字段 |
| 无法抽象出可迁移原理 | 驳回或删除 |

跨目录改名复制仍视为重复。

## 6. 拆分、合并与移动

- **拆分**：每个新条目都要重新通过准入检查；原条目在裁决记录中列出被哪些条目吸收。
- **合并**：选择一个 canonical 名称和路径；稳定编号只有在方法语义延续时保留，已废弃编号不得重新分配。
- **移动**：当前 v7 未生产，不建设旧路径双读或数据迁移器；代码、索引、测试、installer 和文档必须一次性切换。
- **改名**：创作概念别名只放 canonical 归一真源；禁止用复制文件维持旧名。
- **废弃**：正式文件删除，理由与替代去向留在任务裁决中，不在运行时条目保存墓碑字段。

## 7. 内容纪律

- 只写可迁移原理、结构约束、操作方法和失败模式。
- 禁止可直接复刻的具体剧情、人物配置、书名人名和长篇示例。
- 正例只用于说明判定边界，不得成为默认答案模板。
- 硬约束必须能进入作品契约或事实审查；软策略必须允许选择、混合、修改、拒绝和自定义。
- 固定路由只能做 canonical 归一与兼容范围定位，禁止决定具体创意、剧情、人物或章节组合。
- 通用适用范围省略，不用“全部”填充字段。
- 条目正文使用小说创作的语言（作者 2026-07-21 拍板）：用戏、场面、铺垫、伏笔、留白、笔墨、张力、收束等写作行话；禁止工程与产品词汇（容器、轴、投放、载体、门控、断点、闭环、抓手、实例化等）。front matter 字段名与切片标题是运行时契约，不受此条约束；作为条目名称或关键词的既有标识符可保留。
- 条目正文不携带策展溯源（来源编号、吸收记录、审查状态）；这些只保存在任务 research 记录。

## 8. 审查记录

每批策展记录至少包含：

| 项 | 内容 |
|---|---|
| 候选/原路径 | 唯一可定位路径或来源编号 |
| 主要调用者 | 谁在何时使用 |
| 维度裁决 | canonical 归属及边界依据 |
| 近重复 | 对照条目与差异 |
| 内容处置 | 保留、锐化、拆分、合并、移动、废弃、驳回 |
| 字段处置 | 每个机器字段的消费者 |
| 风险 | 模板化、误触、同质化或跨层修改风险 |
| 验证 | 格式、行为测试、独立内容审查结果 |

来源、版本和裁决留在任务记录；正式条目不重复保存这些治理信息。

## 9. 签收与回滚

- 签收角色是开发治理者，不是使用产品写书的作品作者。
- 内容签收确认的是边界、可调用性、非模板化和失败模式，不做逐条评分或热门排序。
- 普通内容按维度或小批次独立提交；发现问题时回退对应提交，不引入运行时兼容层作为回滚机制。
- 架构变更未完成全链测试前，不开始依赖该 schema 的批量内容策展。

## 10. 完成检查

- [ ] 有明确调用者、阶段和产出
- [ ] 通过唯一归属与相邻边界检查
- [ ] 通过近重复与拆分检查
- [ ] 没有成品剧情模板或无消费者字段
- [ ] 生成侧与审查侧各有清晰切片
- [ ] 行为测试和独立内容审查通过
- [ ] 裁决记录与回滚点完整
- [ ] 正式目录只包含签收后的最终条目
