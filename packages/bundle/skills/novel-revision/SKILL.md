# 改稿（Novel Revision）

把审核记录里已授权的处置落实为新一版待审稿。本技能只处理**草稿区范围内的修改**：发现项的 `影响范围` 里带 `世界书`、`大纲`、`作品契约`、`构想`、`账本`、`本书记忆` 任一个词的，一律走提案呈报上游；作者对这类条目说的「保留／驳回／无法判断」可以用**不带新稿正文、不带补丁的纯处置批**记入审核记录，实际上游修改仍只走提案。带新稿或补丁的批次里混进一条上游条目，整批被拒（「须呈报上游」），先按影响范围分组，避免完成改稿后才发现整批不可写入。改写执行者＝**改稿子代理**，主 Agent 绝不亲自写正文；人设与工序在包内 `底本/改稿章程.md`，派发时全文放进任务包。

## 标准流程

1. **读待处理项**：先调 `novel_get_story_status` 取本章 `审核记录哈希`，再读审核记录 `草稿区/审核/卷<NN>-<章名>.json` 中「待处理」的发现项（`发现项编号`/证据位置/问题说明/修改建议/影响范围）。先核对每条编号非空且互不重复——编号为空就回《全面审读》按模块名重新回写补号再来，拿空号批量落实会把一条处置套到所有同号条目上；
2. **汇总处置决定**：逐条定处置（已解决/已接受修改 → 需要改正文；作者保留/已驳回/无法判断 → 只记处置），作者已口述改法的条目把改法原文写进处置清单；
3. **派改稿子代理**（有正文改动时）：任务包＝`底本/改稿章程.md` 全文＋当前待审稿正文＋已授权处置清单（每条含 `发现项编号`/证据位置/问题说明/修改建议/作者改法）＋硬约束（取契约第六分部「创作禁区与不可妥协项」原文与确认细纲的 `〔硬〕` 行）＋契约「叙事方式与文风基调」分部原文。**材料全部内联，不给书仓路径**；子代理返回**整稿新版**与「发现项→改动」映射清单；
4. **批量落实**：调 `novel_apply_revision_batch`（卷/章/章名/`新稿正文`/`处置`/`生成模块`——参数名是 `处置`，传 `处置清单` 会得到「处置清单为空」）；`生成模块` 要显式传 `改稿子代理`，缺省会记成 `改稿`。每次都传上一步拿到的 `审核记录哈希`，成功返回的新哈希供下一批用；哈希不一致、编号未知或同批重复都整批拒绝，先重取状态再来。一次写新稿（`稿<N+1>.md`，版本+1，旧稿降级留档，候选事实段原样带过）并回写全部处置；**只记处置的批次不传新稿正文**，处置里只写编号、处置和必要的改动说明，其余字段、其他发现项与审核证据由工具原样保留；二十条以上的处置也照此一批传，不重传发现项全文；作者自己改的版本用 `novel_import_draft`（角色: 待审稿、生成模块: 作者手改）导入，处置照常回写；
5. 正文或审读依据改变时，按当前输入重跑审核（《全面审读》），确认修复无回归；只有纯处置且输入未变时，不为重复获取相同建议重审。全部处置有效、证据适用当前稿且审核完成后进入定稿准备。

## 小修快路

作者口述的一处小改（改一句、删一段）：直接调 `novel_apply_revision`（单条处置＋补丁旧文/补丁新文），补丁旧文须唯一命中待审稿正文；**补丁只在处置为 `已解决` 或 `已接受修改` 时生效**，配 `待处理` 传补丁会被拒绝。

## 重入（轮次推进）

- 每轮「审读→改稿→复审」算一个改稿轮次，轮次随新稿推进 +1；
- **轮次上限 3**：第 3 轮仍有未解决问题时不再自动发起新一轮——向作者标「须作者决定」，附**瓶颈诊断**（问题集中哪个维度、根因在草稿还是上游设计、可选出路：接受现状入档／退回上游／作者亲自定夺）。这是建议不是门禁：**作者要求继续改就照做**，不把上限当拒绝的理由；
- 出路选「接受现状入档」时，余下条目按作者意见逐条记 `作者保留` 或 `已驳回` 再进定稿准备——留着「待处理」审核判不完成；
- 轮次按草稿目录里 `生成模块` 属改稿或作者手改的稿数数，处置历史以审核记录为准，都不凭会话记忆。

## 工件契约

| 工件 | 路径 | 属性 |
|---|---|---|
| 新待审稿 | `草稿区/草稿/卷<NN>-<章名>/稿<N+1>.md` | frontmatter `角色: 待审稿`、`版本`+1、`父版本`、`生成模块: 改稿子代理`（须显式传，缺省是 `改稿`）;批量落实时 `来源快照` 记处置编号，小修快路不记;旧稿 `角色: 草稿` 留档 |
| 审核记录 | `草稿区/审核/卷<NN>-<章名>.json` | 机器态 JSON（`schemaVersion: 1`）;处置只经工具回写,不手工编辑 |

## 工具

| 工具 | 何时用 | 不要 |
|---|---|---|
| `novel_apply_revision_batch` | 汇总完一批处置后一次落实（新稿＋处置同批） | 传未授权的改动;手工编辑审核记录 |
| `novel_apply_revision` | 作者口述的一处小改；单条纯处置 | 用它做整章重写 |
| `novel_import_draft` | 作者贴自己改过的版本 | 对作者稿再跑润色（作者点名除外） |
| `novel_record_proposal` | 发现项涉及上游真源时，按《工作台总控》“提案与吃书补偿”整理影响面后登记 | 把上游变更混进改稿处置清单 |
| `novel_resolve_proposal` | 作者明确通过或驳回后回写提案决定 | 把建议当成作者决定 |
| `novel_apply_retcon` | 已定稿内容更正，转《定稿沉淀》完成呈报与本次作者裁决 | 用草稿改稿工具覆盖定稿 |
| 改稿子代理 | 一切判断性正文改写 | 让主 Agent 代写;任务包缺改稿章程 |

## 作者介入

- 作者能做什么：自己动手改（贴整版或局部）、指定某几条按自己的写法改、驳回子代理的改动；
- 用哪个通道：贴整版 → `novel_import_draft`（角色: 待审稿、生成模块: 作者手改）；指定改法 → 写进处置清单的 `改动说明` 交改稿子代理执行；
- 主 Agent 接到后：作者手改的稿照常回写处置并进入复审；对 `生成模块: 作者手写/作者手改` 的稿不主动再改一个字，发现项处置一律呈作者。

## Off-limits

- 真源写入限制不放松：真源修改走提案（影响分析前置＋整批确认）；
- 处置与改动一一对应；子代理失败只单点重试，严禁主控代写正文；
- 审核记录只经处置工具改，工具报「审核记录已变化」时重取哈希后重试，不用通用写工具补写 JSON；
- 改稿不产生 git 提交（草稿区不入库）。
