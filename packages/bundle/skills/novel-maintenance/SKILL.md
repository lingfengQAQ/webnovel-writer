# 书仓维护

本技能排查目标书的环境、文件身份、过程工件和格式问题，并处理已有证据支持的 v8/DSH 旧格式。它不补写故事事实，也不代替章节恢复或创作。正常开章不加载本技能，继续使用一次 `novel_begin_chapter`。

涉及草稿身份、章号证据或版本含义时，先读[书仓格式速查](参考/书仓格式速查.md)，再核对目标书。参考只解释结构，不提供当前书的事实；不得读取其他作品作格式样板。

## 按目的分流

| 作者目的 | 入口与边界 |
| --- | --- |
| 只看书仓格式问题 | `novel_check_book({ bookId })`，报告实际受检、未检范围和问题位置 |
| 深入排查书仓阻断 | 按「只读深查」关联工具结果与当前书的实际证据，先查可取得的信息 |
| 修复已识别的旧格式 | `novel_preview_book_upgrade({ bookId })`，按下节核对整仓预览 |
| 续办失败的升级 | 使用原 `operationId`，按「失败续办」处理 |
| 旧章节的半稿或未选稿需确认留档 | 按「旧章节留档确认」预览指定章节，再请求作者明确确认当前清单 |
| 修改计划或设定含义 | 加载 `novel-design`；不得把语义修改混入格式升级 |
| 更正已入档事实或定稿正文 | 加载 `novel-settle`，走 `novel_apply_retcon` 的作者裁决 |
| 修改未定稿正文 | 加载 `novel-revision`；保留旧稿，按已授权处置改稿 |
| 新增或更新记忆 | 使用 `novel_record_memory` 的专门范围与索引协议；更新前先读完整旧文 |

线索字段搬位属于格式维护；改变线索兑现内容属于语义修改。旧分类记忆的无损拆分属于格式维护；添加一条新决定仍是记忆写入。无法唯一判断时，报告原文与缺口，不猜补、不合并、不删除。

## 只读深查

在已明确的目标书和当前会话可用工具范围内，主动收集相关证据，不把能自行读取的字段逐项交给作者查找。先核实书id与书仓归属；身份或路径有歧义时，先澄清目标。

`blocked` 停止升级写入，仍可继续只读取证。不能把“停止执行升级”理解成停止排查，也不能借排查进入写入或续办批准。

1. 保留最近一次工具结果，逐项核对问题代码、路径及未检范围。
   若开章或升级预览没有完成独立的文档检查，可运行 `novel_check_book({ bookId })`。书仓和环境未变化时，复用已有结果，不反复调用同一检查。
2. 使用当前可用的 `read`、`glob`、`grep` 读取问题文件及其关联证据。
   先核对文件头和机器字段；只有定位冲突需要正文时，才读取相关正文。按来源和章节关系扩展，不能读取其他作品作模板。出现读取失败或内容变化时如实报告，不拼接不同时点的文本冒充同一快照。
3. 按下表补足线索，再形成「排查报告」。
   现有工具不能核实的内容仍标为未核实；主控阅读发现的新线索不自动成为升级规则。

| 问题方向 | 可继续取得的证据 |
| --- | --- |
| Git能力或环境不可用 | 核对插件已有错误、可取得的安装版本和参考中的只读版本探测；分别记录终端与插件的结果 |
| 草稿身份、目录或章号矛盾 | 读取原身份字段、目录名、同章确认细纲和定稿元数据。指出具体不一致项，不用稿号猜章号 |
| 材料、审核、定稿准备或来源失效 | 沿现有清单核对目标路径、版本、来源及工具报告的哈希；声明的哈希不等于已验证一致 |
| 收据、锁或事务异常 | 核对已报告路径中的操作编号、状态与关联目标；保留文件，不按名称、时间或孤立字段决定清理 |
| 未知文件、旧形态、读取失败或未检范围 | 核对实际路径、文件类型线索和可读字段；不能把无法解码的文件强作文本，也不把未检项改成通过 |

环境命令与版本边界见[书仓格式速查](参考/书仓格式速查.md)。工具缺失、权限拒绝或Git安全能力不可用时，报告具体限制；不得改用脚本绕过同一限制。无需将故障归咎于作者操作，也不能仅凭操作系统推定Git版本。

### 排查报告

- **已核实的检查事实**：附工具结果、路径和相关字段，说明实际核对范围。
- **可能原因**：列出支持线索与尚未排除的情况，不把推测写成确定根因。
- **缺失证据**：先列无法自行取得的最少信息；需要作者说明实际归属时再询问，不预填章号或答案。
- **下一步**：区分继续只读排查、已支持的升级、原操作续办，以及需要修复插件或另行处理的情况。

可取得的相关证据已查完时，交付报告与剩余缺口。没有新证据不重复相同探测，不把已核实事实等同于作者批准，也不因找到了更多线索就宣布书仓健康。

## 旧章节留档确认

新定稿的留档清单已纳入同一次定稿裁决。旧章节缺少这份证据，且开章无法区分半稿、未选稿和后来新稿时，可调用 `novel_preview_draft_retention({ bookId, 卷, 章, 章名 })`。先核对已有定稿身份和来源，不用稿号猜章号，也不凭“看起来像旧稿”认定留档。

预览只读，列出 `manifest` 的来源稿与完整留档清单、`change` 的定稿元数据差异、`issues` 和 `notices`。`issues` 阻断确认；`notices` 是单独提示，不表示存在新稿或章节未完成。来源稿或必需证据缺失仍不能确认。

- `ready` 且作者已委托办理时，完整呈报清单和差异，用原 `fingerprint` 调用 `novel_confirm_draft_retention`，由工具向作者提问。该次确认表示作者**现在**认定这些工件仅作本章历史留档，不补造过去的批准。预览期间暂停本章写入，等本次结果后再恢复。
- `action: resume` 表示原确认已写入但尚未提交。核对原操作编号和同一清单，再用本次新指纹请求续办；只补原提交，不重新准备或扩大清单。
- `unchanged` 或 `already-committed` 表示已有可信留档证据，无须重复确认。出现新文件、改稿、重命名或来源冲突时，不用旧章入口重新封存来解除阻断。
- `blocked` 时继续只读深查；不手改清单、定稿摘要或收据，不删除文件来绕过核对。当前工具不能证明历史完成与来源时，保留证据并报告缺口。

提交失败时保留全部原文件和收据。处理原因后重新预览指定章节，再按新指纹续办；原因未处理或仍有冲突时停止重试。成功只确认本次留档证据，不修改定稿正文，也不授权开启下一章。

## 整仓预览与执行

执行前暂停写作及自动任务，保持 Git 干净，无写入锁和待处理事务。已核验的未完稿、材料、审核与准备包可以保留；升级不代表章节已收尾。必须整仓可升级；不能挑出局部文件先修，不能把未支持或未检范围当作通过。第一章没有前章，已收尾章节的历史稿可以留档。

1. 调用 `novel_preview_book_upgrade({ bookId })`。
   成功时，读取 `state`、`changes`、`effects`、`issues`、`notices`、`activeWork` 和 `resumable`。预览没有写入。
   `inspectionBefore` 检查原书，`inspectionAfter` 检查拟变换后的内存内容。不能用后者宣称原书已升级。
   `issues` 是执行阻断项；`expectedStaleIssues` 是本计划将造成的材料过期，仍保留在后态检查中。
   `notices` 单独呈报已核实的留档提示，不把它改成阻断项或未检范围。
2. 核对 `state`。
   `blocked` 时呈报阻断项，停止升级写入并按「只读深查」继续取证；`unchanged` 时报告无需升级，不为产生提交重复调用。
3. 若为 `ready`，向作者说明全部文件差异和受影响工件。
   `changes` 的 `before`、`after` 是这份计划的原文与目标内容；不得自行增减目标或改写差异。
4. 使用原始 `fingerprint` 调用 `novel_apply_book_upgrade({ bookId, fingerprint })`。
   工具重新核对计划并请求作者批准。必须由该次作者问答批准，不传 `approved:true`，不用历史批准替代。
   作者已要求办理升级时，呈报差异后进入工具的作者问答；不要先额外问一遍是否执行。作者只要求检查或预览时，不进入执行。
5. 核对返回的写入和提交状态。
   只有 `committed` 才报告本次升级已提交。保留 `operationId`，按实际结果说明后续动作。

批准等待期间，文件、目录、书id归属或规则变化会使原计划失效。重新预览并呈报新差异，不把旧指纹改成新值后冒用原批准。格式变化不提升故事内容版本，不重写正文、来源或事实历史。

旧草稿的文本型身份须与目录同卷同名。章号只能由唯一对应的已确认细纲或定稿证明，稿件 `版本` 不能当作章号。缺少证据时保留诊断，不删除身份或稿件。

缺证据时只询问实际归属或已有证据的位置。不得在问题或选项中预填任何章号，也不为通过升级而编造已确认细纲。作者补充归属仍须按正常流程核验，不能直接照示例补写身份。需要改设计时另行办理。

`activeWork` 列出需呈报的保留工件，批准前逐项说明。Git历史证据不足时，不能仅凭该清单认定历史章节尚未收尾。草稿不进入 Git，完整转换前后文保存在本地维护收据，收据校验值绑定提交。只转换草稿时也有维护提交，但不向 Git 添加稿件。升级后按原章继续，重核报告中受影响的材料与审核证据，不沿用已过期的批准。

## 失败续办

保留收据、事务和当前文件，严禁用文件工具改写或删除维护证据。模型不执行 Git 写命令，不修改文件来伪造成功。

- `written-pending-commit`：文件已写入，提交未完成。处理报告的原因后，用原 `operationId` 调用 `novel_resume_book_upgrade({ bookId, operationId })`；该工具先核对并呈报本次续办，再请求作者批准。它只补原提交，不重新转换文件。
- 写入中断：使用原操作编号调用同一续办工具。返回 `recovered` 只表示中断文件批次已恢复；必须重新预览并请求新的升级批准，不能报告升级完成。
- `already-committed`：已有完整历史提交证据。本次没有重复变换或新增提交，无须补交。
- 仍失败、收据损坏或当前文件有冲突：停止重试，呈报原因和原操作编号。不得覆盖作者后来的修改，也不删除证据后重新升级。

提交输出只有换行警告时，不足以证明失败原因。先报告原因尚未核实，核对真实错误；不要把警告当根因，也不要自行删除Git钩子或改配置来强行提交。原因未处理时不反复请求续办批准。

续办用于完成或恢复原失败操作，不是主动撤销入口。当前没有主动撤销工具；需要撤销已成功升级时，先呈报目标与后续改动，不自行 reset、checkout 或 revert。

## 受影响工件

按 `effects` 逐项报告材料、审核、准备包、引用行号或缓存的影响。保留旧证据和作者稿，不改哈希来沿用旧批准。只对实际依赖变化的工件安排复查；需要模型的重建必须有相应授权，不自动重跑所有章节。

升级的成功只证明本次规则与文件批次，不证明文学语义正确，也不授权继续写作、开启新章或发布。
