# 日常写作与恢复

当前源码的 DSH 0.2 交互见[结果卡与导出成品](result-cards.md)，其中明确了开发版与已发布 8.0.0 的版本边界。

## 继续章节

明确书名和范围，例如“继续这本书的第2章，先核对进度”。工作台会读取实际书仓，再决定需要准备细纲、写稿、审读还是定稿。换会话无需手动重建一份当前章节状态表。

## 修改设计或正文

通过书房编辑器保存草稿、规划或世界书后，让工作台核对影响。保存文件、提交版本、工作台理解修改是三件不同的事。若保存时报告版本冲突，先重新读取当前文件，避免覆盖更新。

在当前主对话打开书房并保存后，检查保存结果：文件已保存表示磁盘已更新；版本已提交表示已留下 Git 记录；已交给主控表示通知送达，仍需看主控后续的读取和核对结果。只有标点或局部措辞变化，核对后可以直接结束；改变事实、人物目标或写作约束时，应说明受影响内容和待你决定的事项，不会因此自动重写下游或推进下一章。

如果在外部编辑器或终端改了文件，它没有经过书房的保存通知。回到对应作品的对话，可以直接说：

> 我刚修改了《书名》的作品契约，把主角目标从复仇改为寻找真相。请读取当前文件，核对大纲、世界书和已定稿章节的影响，列出需要调整的地方，先不要改稿。

不需要专门的隐藏命令。“刷新书房”同步目录与已打开正文；有未保存编辑时保留文字并提示比较，它不能代替这条核对请求。主控忙碌或被中断后，也可以说明文件和改动目的，请它从当前文件重新核对；不要为了唤醒它反复保存相同内容。

修改未定稿内容时可返回相关流程；涉及既有定稿的设定变化需要核对影响并走补偿/修订流程，不要直接改已确认的设计文件或手写账本来绕过检查。

## 审核失败或模型中断

先看失败来自正文问题、材料不足、配置/网络，还是作者意见。补足材料或修复服务后继续对应步骤。模型输出的一句“完成”不能替代实际审核记录或提交结果。

## 暂停

可明确要求暂停当前章。下次开始先核对文件与 Git 状态，已完成部分可继续使用；取消或失败不是对后续写入的批准。暂停期间不要在别处手工改动同一章的文件。

## 卷末

卷末先核对计划章节、定稿和未回收事项，再准备卷摘要候选，经核对后确认。窗口用尽不等于整卷完成；无法确定时应显示未知或待核对。开始下一卷前核实前卷沉淀与当前卷规划。

## 导出

指定书、卷/章节范围和新的目标目录，导出包含定稿合集与来源清单。先检查冲突再写出，读取实际文件校验通过后交付成品卡；卡片不可用时明确提供路径，不重复写盘。导出不把草稿混入定稿。平台排版或发布仍由你审核，工作台不会代你向小说平台投稿。
