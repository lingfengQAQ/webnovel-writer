# 故障排查

先记录精确的包、DSH、Node、OS 版本和最后成功步骤。公开日志只保留必要片段，移除 token、API key、用户目录和作品正文。

| 现象 | 检查与处理 |
| --- | --- |
| 找不到 dsh/pnpm | 新开终端，核对 Node/npm 全局安装目录是否在 PATH，再查看 `dsh --version` |
| 安装插件报 `ERR_PNPM_ADDING_TO_ROOT` | 终端里的 pnpm 不是 11.27.1；`pnpm --version` 核对后重装指定版本 |
| 启动后没有 Web 页面 | 确认自定义 profile 来自 `--from-default-profile web`，基础 profile 不自动变成 Web |
| 安装 tgz 报路径被拆开 | 将文件放到有写权限的无空格目录；仅外层加引号可能不足以解决当前宿主转发限制 |
| 安装时出现 missing peer 提示 | 宿主提供这些组件；实际启动缺模块时，按下方版本修复步骤核对宿主与插件组合 |
| 升级后设置消失、插件加载报 API 不存在或会话格式错误 | 先核对精确 DSH 版本和插件来源，不通过反复安装 latest 或删除数据试错 |
| 页面连接被拒绝 | 使用当前启动进程给出的完整链接，确认端口和进程仍在；不要复用过期 token |
| 端口已占用 | 换空闲端口；确认不是重复启动同一 profile |
| 工具或技能出现两份 | 同一 profile 里主包和完整版只能留一个；停止实例，卸载多余的那个再重启 |
| 模型认证、额度或限流失败 | 在宿主设置核对服务、模型与凭据；先发短消息，不反复重跑昂贵章节 |
| 向量维度不匹配 | 核对实际模型输出维度及高级设置里的“将维度参数发送给 API”，配置改变后重建对应索引 |
| 检索回退/场景识别失败 | 查看可选服务状态；基础检索可能仍可用，回退不等于增强服务成功 |
| 编辑保存冲突 | 重新读取当前文件与版本，核对他处修改，再保存；不要强盖 |
| 进度与聊天印象不同 | 让工作台重新核对实际书仓；模型文字不是定稿或提交证据 |

提交 Bug 时附最小合成复现、精确错误和相关文件名即可。内容损坏先完整备份现场，不要手动删除或改写书仓里的文件来尝试“清空恢复”。

## DSH 版本不对怎么修复

先按 [安装教程的版本对应表](install.md#为什么要固定-dsh-版本) 确认目标：8.0.0 / 检索增强 8.0.0 用 **0.2.0-rc.2**，旧版 preview.6 / 提供方 0.0.8 用 **0.1.5-rc.2**。宿主版本不匹配会影响设置、工具与会话接口；更高版本也不代表已经兼容。

1. 停止正在运行的 DSH 实例，按 [备份说明](upgrade-backup.md) 保存作品目录和 DSH home。更换版本后必须重启，已运行进程不会自动换成新版本。
2. 在 PowerShell 检查实际命令与版本：

   ```powershell
   dsh --version
   pnpm --version
   Get-Command dsh -All | Select-Object CommandType, Source
   npm prefix --global
   ```

3. 如果当前是 npm 全局安装，按选定组合精确重装。以下命令对应 **8.0.0 / 检索增强 8.0.0**：

   ```powershell
   npm install --global pnpm@11.27.1 @deepseek-ai/dsh@0.2.0-rc.2
   ```

   若使用已发布 preview.6，应将末尾改为 `@deepseek-ai/dsh@0.1.5-rc.2`，并使用对应已发布插件；不要与 8.0.0 / 检索增强 8.0.0 混装。其他安装渠道使用其自己的版本管理方式。

4. 关闭并重新打开终端，再执行 `dsh --version`。仍显示旧版本时，通常是 PATH 中存在另一份 DSH，或 PowerShell 有同名别名/函数。用上面的 `Get-Command dsh -All` 找到优先命中的路径，与 npm 全局目录比较；切换到正确安装目录，或通过原安装渠道移除多余安装。不要删除 profile、会话或书仓来修 PATH。
5. 确认插件包来自同一兼容组合，再执行 `dsh --profile scriptor --dump-config` 并重新启动。先用临时工作区核对书房、设置卡片和技能；配置能输出只说明组合配置可读，不能代替实际启动检查。

**已经被较新 DSH 写入的会话不要直接交给旧版读取。** 0.1.7 使用 v4 会话格式，降级安装程序不会把日志改回 v3。保留当前现场；需要回退时使用升级前的完整备份和与之匹配的版本，在副本中验证后再恢复。没有升级前备份时，先保持能够读取该会话的版本并排查，不手改会话格式号。

版本和来源都正确仍失败时，保留精确错误、`dsh --version` 输出及实际命令路径，再提交最小复现；不反复更换宿主版本尝试修复。

## 旧书卡在世界构建

preview.5 或更早创建、未使用占位设计流程的书，可能已有已确认的人物和规则，却没有在 `世界书/模块声明.md` 登记对应模块。preview.6 已修复新建书的默认声明，**升级不会自动改写旧书**。

先完整备份书仓，停下正在写这本书的会话。用文本编辑器查看 `世界书/模块声明.md`，保留所有现有内容，只补缺少的行，各保留一份：

```markdown
- 人物档案
- 世界规则
```

保存后重新让工作台核对书仓进度；两个模块各自仍需至少一条已确认条目，补声明不会自动补设定正文，也不代表书已定稿。若文件损坏或已有复杂模块声明，保留现场并先排查，不整份替换。

## 设计确认或审核停住

- 提示 `FS_NOT_OBSERVED`：让主会话先用原生读取工具读目标文件，再调用设计工具；进度卡、书房预览不代替该读取。
- 提示 `FS_STALE_VERSION`：目标被作者或其他会话修改过，重读并核对差异后再确认，不强行覆盖。
- 提示窗口未就绪：第一章章名须与近期窗口中一条可进入条目同名；先核对实际条目，再经设计工具修正。preview.6 会直接列出可进入名称。
- 显示「已确认但无内容」：确认标签仍保留；8.0.0 会把必要内容缺失纳入就绪建议，先补真实正文，合法远期留白无需强行填满。
- preview.5 显示「完成: false」却「尚待回写模块: 无」：属于已知审核清单问题，不能据空清单当成审核完成；升级到 preview.6 后重新运行审核。

## 保存后反复更新契约

### 保存后没有反应

先区分改动入口和停在哪一步：

- **外部编辑器或终端修改**：回到该书的对话，说明改了哪个文件、改动目的，请工作台读取现文件并核对影响；刷新书房只更新文件树。示例见 [修改设计或正文](workflows.md#修改设计或正文)。
- **书房编辑器保存**：检查文件保存、Git 提交和主控通知的各自结果。提交失败用编辑器的重试提交；通知失败用通知重试，已保存内容不必重写。
- **已交给主控，但没有核对结果**：查看正确的主对话是否仍在运行或已被停止。可发送“继续核对刚才对某文件的修改，先报告影响，不改其他文件”。送达通知不等于模型已经处理完。
- **模型只输出 `<invoke ...>` 等文本**：这不等于真实工具调用。核对界面是否实际出现工具执行结果；若没有，可要求重新使用工具读取。记录宿主/模型版本、操作入口和脱敏结果供排查，不把模型打印的调用文本当读取证据。

### 反复执行同一个无改动操作

先停止当前任务，按 [升级步骤](upgrade-backup.md) 更新到 8.0.0 及对应宿主后重启。保存后只需核对本次修改和影响；“内容与已提交版本一致，无需补提交”表示已经完成，不需要再添加文字来产生提交。若编辑器提示提交失败，使用编辑器的重试提交入口。

## 历史设计显示疑似模板占位

8.0.0 会把与旧 seed 整份计划模板一致的未匹配项列为“疑似模板占位待核对”，不会自动删除原文或替你确认计划。读取所列来源，说明这些条目是实际计划还是尚未补全的模板；再委托工作台通过原有设计工具修正或补全。只有事件同名不会触发过滤；待核对也不等于已兑现或无偏离。
