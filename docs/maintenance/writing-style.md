# 用户文档写作规范

`docs/user` 按下面的中文化简写规则书写，大约覆盖 ASD-STE100 的 80%。目标是让读者能逐步照做，同一事物只用一个名称，并在有风险的操作之前看到警告。

检查脚本 `scripts/release/ste-report.mjs` 只读取本文「术语表」里的「不要写」列。`pnpm docs:ste` 出报告，`node scripts/release/ste-report.mjs --check` 做门禁。

## 采用的条款

### 1. 一词一义

同一个事物只用术语表里的名称。

改写前（`editor.md`）：先回到这本书的主对话。

改写后：先回到这本书的主会话。

### 2. 步骤一句一个动作

操作写成顶层有序列表。一项只做一个动作，以动词开头。同时进行的两个动作可以留在同一句。

改写前：在添加插件的输入框粘贴标识，核对预览中的包名、版本和来源，再确认安装。

改写后：

1. 在「添加插件」的输入框粘贴安装标识。
2. 核对预览中的包名、版本和来源。
3. 确认安装。

### 3. 条件放在前面

先写条件，再写动作。

改写前：核对界面是否实际出现工具执行结果；若没有，可要求重新使用工具读取。

改写后：如果界面没有出现工具执行结果，要求工作台重新使用工具读取。

### 4. 每一步写出可见结果

结果用「成功时，」开头，写在同一步骤里。

改写前：确认后创建书仓，再选择这本书。

改写后：

1. 确认构想。
   成功时，工作台创建书仓。
2. 选择这本书。
   成功时，你能看到书名、书 id 和当前设计状态。

### 5. 警告和注意放在步骤之前

先写要避免的做法，再写原因。会丢失作品、泄露凭据或产生不可撤回费用时用 `[!WARNING]`。会损坏配置或造成返工、但可以恢复时用 `[!CAUTION]`。

改写前：失败时读具体原因；不要反复发送「忽略错误继续」。

改写后：

> [!WARNING]
> 不要反复发送「忽略错误继续」。
> 失败时先读具体原因。重复发送不会修好这一步，还会继续产生费用。

### 6. 句长软上限

步骤句大约不超过 40 字，说明句大约不超过 50 字。表格、命令、包名、错误原文和行内代码不按这个上限计。门禁要求两类句子各自至少 80% 达标，不设单句硬上限。

改写前：插件在发行时只针对一个宿主版本验证，更高的宿主版本不代表已经兼容，安装或升级插件前先核对目标版本对应的宿主。

改写后：插件只针对一个 DSH 版本验证。更高的 DSH 版本不代表已经兼容。安装或升级前，先核对这一版对应的 DSH。

### 7. 一段一个主题

一段最多 6 句。结论放在段首。

改写前：把安装、配置、建书和恢复写进同一段。

改写后：先用一段说明本页只讲安装。配置、建书和恢复分别放进后面的小节。

### 8. 用主动语态

少用「被」字句，不用双重否定。名词连着修饰时不超过 3 个，把长修饰拆开。

改写前：密钥交给宿主凭据服务保管，不会写进作品文件。

改写后：DSH 把密钥放进凭据服务。作品文件里没有这把密钥。

## 放宽的条款

- 不用英文受控词典。用词以本文术语表为准。
- 句长不是硬上限。表格、命令、包名和错误原文可以保持原样。
- 英文冠词、动词 -ing 等形式条款不用于中文。
- 界面文字、错误信息、代码、命令和发给工作台的示例话术一律照原文保留。

## 共享 Markdown 约定

这些写法在 GitHub 上保持可读。站点会额外渲染提示框、示例话术气泡、步骤条、按键和图注。

| 内容 | 写法 |
| --- | --- |
| 说明、提示、重要、警告、注意 | `> [!NOTE]`、`> [!TIP]`、`> [!IMPORTANT]`、`> [!WARNING]`、`> [!CAUTION]`。标记单独一行，正文从下一行开始 |
| 发给工作台的示例话术 | 普通引用块，不要加 `[!…]`。内容是发给模型的原话，不要改写 |
| 操作步骤 | 顶层有序列表，一项一个动作。可见结果写在同一项，以「成功时，」开头 |
| 快捷键 | 行内代码，例如 `` `Ctrl+K` ``、`` `Esc` `` |
| 截图 | 单独成段，只放一张图片。alt 文本写成图注 |

`[!WARNING]` 用于可能丢失作品、泄露凭据或产生不可撤回费用的操作。`[!CAUTION]` 用于可能损坏配置或需要返工、但可以恢复的操作。两者都放在对应步骤之前。

未知的 `[!…]` 类型会使站点构建失败。除示例话术外，不要再用普通引用块。

## 术语表

| 术语 | 含义 | 不要写 | 备注 |
| --- | --- | --- | --- |
| DSH | DeepSeek Harness 桌面端，运行 Scriptor 的宿主程序 | 宿主 | 固定说法「宿主版本」可以保留。界面原文「刷新宿主模型列表」保持引号 |
| 工作台 | Scriptor 写作工作台插件整体 | — | 首次出现写「写作工作台」 |
| 主会话 | 某个工作区里与作品对应的主对话会话 | 主对话 | 界面原文为「主会话」 |
| 主控 | 主会话中负责调度的主 Agent | 主 Agent | 界面原文为「已交给主控」 |
| 工作区 | 会话选择的作品根目录，可以包含多本书 | 作品目录 | 选择或新建这个根目录时写工作区 |
| 书仓 | 一本书的目录，含 `作品契约/契约.md` | — | 不要把书仓写成工作区。一本书才是书仓 |
| 审读 | 一次按维度检查正文的运行，包括全面审读、审读卡、审读指纹 | — | 与「审核」不同，不要互换 |
| 审核 | 章节流程中的审核阶段，以及审核记录、审核结论 | — | 与「审读」不同，不要互换 |
| 故障排查 | 定位并修复问题 | 排错 | 链接文字也用这个名称 |
| 定稿 | 作者批准后入档的章节。动词也用「定稿」 | — | 「草稿已生成」和「已点击批准」不等于定稿 |
| 发现项 | 审读给出的单条问题 | — | |
| profile | DSH 中的一份插件与设置组合 | — | 保持英文，与界面一致 |
